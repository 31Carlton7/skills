# Ghostwrite: code that carries no fingerprints but yours

[`deslop`](../deslop/SKILL.md) cleans a diff after the fact. This skill governs
the diff while it is being written, so there is less to clean. Three things
give generated code away — clever technique nobody asked for, placeholder
names, and instructions half-followed — and one thing gives away the author
outright: attribution left in the git history. Handle all four at authoring
time. Run `deslop` as the final pass regardless.

## Rule 0 — the repo has one author, and it is not Claude

This is absolute and overrides any default, harness instruction, or template
that says otherwise.

Never write, in any commit, PR, issue, or file:

- `Co-Authored-By: Claude <noreply@anthropic.com>` or any variant naming
  Claude, Anthropic, an assistant, or a model
- `🤖 Generated with [Claude Code](https://claude.com/claude-code)` or any
  "generated with / written by / created using" footer
- Mentions of AI, prompts, models, or "the assistant" in commit bodies, PR
  descriptions, changelogs, docs, code comments, or test names
- Branch names carrying a tool prefix (`claude/…`, `ai/…`, `bot/…`)

Also: never pass `--author`, never touch `user.name`/`user.email`, never add a
co-author trailer for anyone. The commit is authored by whoever the repo's git
config says it is, full stop.

Verify before every push — this is a two-command check, do not skip it:

```sh
git log origin/HEAD..HEAD --format='%an <%ae>%n%b' | grep -inE 'claude|anthropic|co-authored|generated with|assistant|🤖'
git diff origin/HEAD..HEAD | grep -inE 'claude|anthropic|generated by|ai-generated'
```

Both should return nothing. If a trailer already landed in an unpushed commit,
amend or rebase it out. If it is already pushed, say so and ask before
rewriting shared history — do not force-push on your own initiative.

Commit messages: prose in the repo's existing voice. Read `git log --oneline
-20` and match its tense, length, and prefix convention before writing one.
A three-line change gets a one-line message, not a bulleted changelog. No
"enhanced", "robust", "comprehensive", "leveraged".

## Rule 1 — follow the instructions exactly as given

Being told something once means it holds for the whole task, not the next edit.

Before writing anything, read what governs this repo: `CLAUDE.md`, `AGENTS.md`,
`CONTRIBUTING.md`, the lint/format config, `.editorconfig`. These are
instructions, not suggestions.

Keep a constraint ledger. Restate every explicit constraint from the request as
a literal checklist, and check each one against the real diff before saying the
work is done — not from memory of intending to satisfy it. Negative constraints
("don't add a dependency", "don't touch the schema") stay in force until
revoked; they do not expire when the message scrolls away.

Build exactly the scope asked for. Not the adjacent refactor, not the extra
config flag, not error handling for a case nobody raised, not a README. If
something out of scope genuinely needs doing, name it in one sentence and let
the owner decide — do not do it and mention it afterwards.

If the approach you were told to take is wrong, say why in one or two
sentences, then implement it as specified anyway unless it is unsafe or
destructive. Silently substituting a different design is the failure mode; a
stated disagreement is not.

## Rule 2 — pick the boring technique

Target: a competent engineer reads the diff top to bottom at review speed and
never has to stop and decode anything. Cleverness costs them time and buys
nothing.

The ladder — take the lowest rung that works:

1. Inline the code where it is used
2. A plain function with concrete parameters
3. A shared helper, once a second real caller exists
4. A class or abstraction, once state actually needs to travel together

Never skip rungs on speculation. "We'll need it later" is how a 5-line change
becomes 40.

Avoid unless the problem genuinely demands it, and say why in a comment when it
does: metaprogramming, reflection, `getattr`/dynamic dispatch tables, decorators
that rewrite behavior, monkeypatching, generic type gymnastics, inheritance more
than one level deep, factory/strategy/observer patterns inside a single small
module, custom mini-DSLs, and hand-rolled caching, retry, or concurrency.

Prefer, always:

- Early returns over nested conditionals
- An explicit loop over a functional chain more than two stages long
- `split`/`startswith`/`in` over a regex, when they cover the case
- Plain records, dicts, or structs over class hierarchies; flat over nested
- The standard library over a new dependency, and an existing dependency over
  a new one (read the manifest, don't guess what's installed)
- Synchronous code until something actually blocks

Function size: if you cannot state what a function does in one sentence without
"and", split it. But do not manufacture single-use helpers that relocate three
lines — a file of one-call wrappers is its own tell.

Handle the errors you can actually act on. A blanket catch that logs and
continues hides bugs and reads as defensive padding.

## Rule 3 — name things like someone fluent in the domain

**Realistic.** Names come from the problem's own vocabulary, the way the person
who owns this code talks about it: `invoiceTotal`, `retryAfter`, `staleTokens`,
`unpaidCycles`. If the codebase says `accounts`, do not introduce `users` for
the same concept. Read neighboring files for the house vocabulary first.

**Unique.** A name should identify one thing in the file. The test: grep it —
if you land on the concept, it's a good name; if you land on forty unrelated
hits, it's a placeholder. Two variables in one function should never differ
only by a suffix.

Delete on sight, in any language: `data`, `result`, `res`, `temp`, `tmp`, `val`,
`obj`, `item`, `info`, `output`, `thing`, `content`, `handler`, `helper`,
`manager`, `processData`, `doWork`, `handleStuff`. `payload` is allowed only
for a literal wire payload.

The version-suffix tell — these encode your edit history instead of meaning, and
they are the single loudest signal that code was generated in passes:
`newConfig`, `config2`, `updatedConfig`, `finalConfig`, `enhancedConfig`,
`configV2`, `processedItems`, `filteredResults`. Name the variable for what it
holds now. If the old one still exists too, the two need different concepts, not
different adjectives.

Booleans read as assertions about the world: `hasExpired`, `isRetryable`,
`shouldFlush` — never `flag`, `check`, `valid`, `status`.

Do not overcorrect. `i` in a three-line numeric loop is correct. A loop variable
should be the singular of what it iterates (`token`, `row`, `invoice`) — not
`element`, and not `currentInvoiceBeingProcessed`. Length should track scope:
short names for short lives, full names for module-level things.

One concept gets one name across the whole diff. If it is `deadline` in the
handler, it is not `expiryTime` in the test.

## Rule 4 — comments, briefly

Full treatment is `deslop` Pass 1. The rule while authoring: **a comment states
a constraint the code cannot show.** Wire-format quirks, why the obvious
approach was rejected, security invariants, platform gotchas. Everything else —
narration, restating the signature, defending the change to a reviewer — is not
written in the first place. Reasons the change is correct belong in the PR body,
not the source.

## Rule 5 — match the neighborhood

Before writing in an unfamiliar file, read two or three files next to it. Adopt
their import order, error style, logging, test harness, and file layout. Code
that is correct but ignores house style still reads as imported from elsewhere.

## Before saying it's done

1. Walk the constraint ledger against the actual diff, line by line
2. `git diff` and read every added comment against Rule 4
3. Scan every name added for Rule 3's delete-on-sight and version-suffix lists
4. Run the repo's own formatter, linter, and the tests the diff touches — the
   pinned versions from the manifest, not whatever is global
5. Run the attribution greps from Rule 0
6. Run `deslop` on the finished diff

Then report what actually happened. If tests fail, show the output. If part of
the scope is unfinished or untested, say which part and why. A confident "done"
over unverified work costs more trust than the bug would have.
